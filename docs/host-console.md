# ホスト管理コンソール

アプリ配布物とは独立した運用ツール（1.2.1）。配布済みのWeb・API版を選択して起動できる。
ホスト自身で http://127.0.0.1:18091/ を開く。外部公開・Firewall変更は不要。

## 導入

管理者PowerShellでプロジェクトルートから `./tool/install_host_console.ps1` を実行する。
既存PdfViewerHostReleaseと同じPython・ユーザーを使い、PdfViewerHostConsoleを
S4U/Limited・OS起動時で登録する。パスワード入力なし。
デスクトップの「PDF Viewer Console」から開ける。

## 監視と操作

- 更新タスクが停止（Ready）している場合も再起動ボタンを利用できる。古い状態報告に妨げられず、ロックとポートの解放を確認して起動する。
- 状態ファイルの一時的な使用中エラーは再試行する。定期状態報告の保存失敗はログに残して次の監視で再試行し、APIの稼働を維持する。

- 「配布済みWebバージョン」からinbox内の配布版を選び「選択版を適用して起動」。WebとAPIを同時に切り替える。
- 選択版は再起動後も固定。別の配布版に変更するときも同じ操作を行う。
- 「稼働中Webを停止」でWeb・APIを正常停止する。更新エージェントは操作受付のため稼働を続け、OS再起動後も停止を維持する。
- 操作待ち・展開・実行環境準備・起動テスト・切替・応答確認・失敗を表示し、適用中の重複操作を防ぐ。
- 既存導入環境では `host_release_agent.py` とコンソールのPython/HTMLを更新し、各タスクを再起動する必要がある。旧エージェントでは操作ボタンを無効化する。エージェント更新は既存の正常停止手順で停止確認後に行う。

- 15秒ごとにAPI /health、Web HTML、/version.json、更新タスク、CPU・メモリを確認。
- 配布版・API版・Web版を照合し、更新中・不一致・応答待ちを区別。特定バージョンを固定しないため、今後の更新・ロールバックも追従する。
- 更新中と配布先変更後5分間は管理画面側の自動復旧を待機。状態ファイルが古い場合も再起動しない。
- CPU・メモリの直近60回をグラフ化。管理コンソール再起動時にグラフはリセットされる。
- 通信断から自動再接続する。コンソール再起動後の操作用トークンも再取得する。
- Webの確認はサーバーのHTML・版情報の応答。すでに開いている別ブラウザーのキャッシュやFlutter画面内の動作までは保証しない。
- report/status.jsonは実応答とは別に表示。取得時刻が60秒以上古ければ画面を未確認表示。
- CPUまたはメモリ95%以上とAPI失敗が5分継続した場合のみ追加の復旧を試みる。
  通常のAPI障害は既存エージェントの監視が先に対応する。
- 手動・自動とも更新適用中は見送り、30分間隔・24時間に最大2回。
  上限はconsole-settings.jsonに永続化。チェックボックスで自動復旧を停止できる。
- agent.stopで正常停止を要求し、タスクReady・agent/serverロック解放・ポート解放を確認して
  Start-ScheduledTaskを実行。タイムアウト時は強制終了せず、追加起動もしない。
- 実行結果はconsole-events.jsonl。設定・ログはD:\PdfViewerHost内、配布releasesの外。
- 更新エージェントも一時停止する。API停止中に通信は失敗し得る。
  Windowsの再起動、DBコピーによる上書き、旧更新監視の再有効化はしない。

## 確認・停止

`Get-ScheduledTask -TaskName PdfViewerHostConsole` とローカル画面で確認。
本番での再起動ボタン試験はサービスの短時間停止を伴う。
OS起動前ログインなしの確認は次回の予定された再起動時に行う。
管理コンソールだけを停止する場合は、自動復旧をオフにして処理中でないことを確認してから
`Stop-ScheduledTask -TaskName PdfViewerHostConsole` を実行する。
API・更新エージェントのタスクは停止しない。
