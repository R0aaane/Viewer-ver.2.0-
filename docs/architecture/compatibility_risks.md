# 互換性リスクと改善候補

| 確認した差異／経路 | 影響 | 対応案・判定方法 |
|---|---|---|
| 指示書のRepositoryとFastAPIは既に存在。Android実装は android_folder_repository.dart、メタデータ管理は server/services/metadata_store.py | 同名の新基盤や一律のORM移行は既存クライアント・ホスト更新に波及 | 現行の factory、API、sqlite3 を維持。追加ルーターと専用DBを契約テストで隔離 |
| Windows のページ取得は folderRepository.dart で直下を全列挙・ソートしてから sublist。進捗件数を求める再帰経路にも列挙が複数ある | ページを進めるたびに同じ I/O が発生し得る | 3万件で初回・次ページ・変更直後の列挙回数と時間を測る。再現時のみ、改名・追加で無効化する索引を検討 |
| 原画像を readAsBytes する経路がある。既存キャッシュのバイト上限は個々のキャッシュに適用 | デコード後のメモリや同時表示のピークは別に発生 | 大画像を含むテスト素材で RSS とデコード数を記録。OOMは今回未再現 |
| RemoteMediaRepository のサムネイル／プレビューは件数でトリムし、キーには mediaId・更新情報等を使う | サイズの偏り、サーバー切替時の同一ID・更新情報を要検証 | 2サーバーで同じIDを返す試験とディスク使用量の測定。新キャッシュはライブラリID別に管理 |
| 認証は設定トークンが空なら通過。既存アプリのAPIトークン保存先は SharedPreferences | 既存ホストをそのままVPNに載せると生成・変更APIの端末別失効を保証できない | 公開前から新ルートは認証必須。旧トークンの一括置換を避け、OSの資格情報ストア・Webセッションを別途検証 |
| 文書URI／パスの改名はID変更を伴う。タグにはホストミラー経路もある | 古いIDの参照やタグの二重更新、権限例外の可能性 | 実機で永続権限・改名・再起動・権限失効を試す。現時点で例外の再現は未確認 |
| Web とネイティブの画面入口が異なる | 片方の画面追加だけでは同等の操作が提供されない | API契約は共通化し、入口・認証・キャッシュはそれぞれで試験 |

今回確認したのは上記の実装経路。実測前の性能値、全端末での不具合、既存の認証で保護される範囲は断定しない。
