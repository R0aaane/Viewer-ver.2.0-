# 作業手順

## 開始・探索・完了
目的、対象、変更禁止部分、完了条件、検証方法を短く整理する。小さな作業で専用計画書は作らない。指定ファイルから原因候補・影響を確認し、最小差分で修正する。

PowerShellの各コマンドはルートで次の確認を先に実行する。作業内容もルート前提で妥当か判断する。

```powershell
Get-Location
if (-not (Test-Path -LiteralPath pubspec.yaml)) { throw 'Project root required' }
```

テストは [既存の検証資料](../architecture/test_strategy.md) から影響範囲に合わせて選び、コマンドで実行する。大きな変更、DB/API境界や統合に影響する変更は広域確認を省略しない。終了コードを確認し、失敗は重要なエラーと周辺行を読んで原因を調べる。過去の合格ログを流用しない。

完了条件: 依頼充足、制約維持、必要な検証成功、差分確認。下記の版更新対象では、版番号整合とWindows Release更新確認も必須。実行不能・未解決なら未完了部分と理由を報告する。不要な検証反復や追加改善をしない。

## 版更新と必須ビルドの対象
AGENTS.mdやドキュメントだけの変更では、バージョン更新とWindows Releaseビルドは不要。文書の参照先・内容整合・差分を確認する。

アプリコード・依存関係・ビルド設定等の変更を含む場合は、従来どおり関連テストと必要な広域検証を実行し、以下を同じ版へ更新する（2026-11-12に参照先を確認）。Webも同時更新する。

- `pubspec.yaml`: `version`
- `lib/services/app_version_service.dart`: `_fallbackAppVersion` の既定値
- `lib/web/web_remote_viewer_page.dart`: `PDF_VIEWER_APP_VERSION` の既定値

`flutter build windows --release` をルートから実行する。SDKの絶対パスは使用しない。開始時刻を記録し、終了コード0に加え `build/windows/x64/runner/Release/pdf_viewer.exe` の更新時刻・版番号を確認する。ログをファイルへ保存する場合はUTF-8を明示し、必要なエラーだけ出力する。Web成果物の生成・配布が依頼に含まれる場合は対応するビルド・配布確認も行う。

調査のためにホスト自動更新・配布スクリプトを起動しない。本番DBや素材を試験用に変更しない。

## コンテキストと出力
全文読込は必要性を判断してから行う。独立した検索をまとめ、結果の件数・行数を制限し、足りない場合だけ拡張する。ログの切り捨てを成功の証拠にしない。

引継ぎは目的・制約・確定事項と根拠・変更ファイル・検証結果・残作業に限定する。一時的な進捗や未検証エラーを恒久Knowledgeにしない。完了報告は変更ファイル、変更点、実行した検証と限界を簡潔に示す。
